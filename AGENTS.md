# AGENTS.md

Инструкции для AI-агентов, работающих с репозиторием **tennis-tournament**.

## Overview

Web-приложение для организации теннисных турниров: игроки, регистрации, матчи, сетка (bracket).

**Стек:** Django 5 + DRF · React 19 + Vite (TypeScript) · PostgreSQL 16 · JWT (`simplejwt`).

| Сервис          | Порт |
|-----------------|------|
| PostgreSQL      | 5432 |
| Django          | 8000 |
| Vite dev server | 5174 |

## Layout

```
tennis-tournament/
├── docker-compose.yml   # только Postgres
├── Dockerfile           # production: Vite build + Django/Gunicorn
├── .env.example
├── backend/             # Django project `config`, app `core`
└── frontend/            # Vite + React + TS
```

### Backend (`backend/`)

- `config/` — settings, root URLs, ASGI/WSGI
- `core/models/` — `User`, `Player`, `Tournament`, `TournamentRegistration`, `Match`
- `core/serializers/`, `core/views/` — DRF по доменам
- `core/urls.py` — router: `players`, `tournaments`, `registrations`, `matches`, `users`
- `core/auth_urls.py` — `/api/auth/token/`, `refresh`, `verify`, `register`
- `core/permissions.py` — `RolePermission`, `IsAdminUser`
- `core/tests/` — pytest + pytest-django

### Frontend (`frontend/src/`)

- `api/` — HTTP-клиент и API-модули (`http.ts`, `players.ts`, …)
- `auth/` — `AuthContext`, `RequireAuth` / `RequireEdit` / `RequireAdmin`
- `pages/` — страницы по доменам (players, tournaments, matches, users)
- `components/` — shell, формы, модалки
- `types/` — TypeScript-типы, зеркалящие API

## Architecture & domain

### API

- Префикс: `/api/`
- Auth: JWT Bearer; refresh через `/api/auth/token/refresh/`
- Vite proxy: `/api` → `http://localhost:8000`
- Production: Django отдаёт SPA (`index.html`) и статику; API тот же `/api/`

### Roles & permissions

| Кто            | Права                                      |
|----------------|--------------------------------------------|
| аноним         | только чтение (GET/HEAD/OPTIONS)           |
| `player`       | только чтение                              |
| `organizer`    | create/update, без DELETE                  |
| `is_staff`     | полный CRUD; раздел users — только staff   |

На фронте: `RequireEdit` (organizer/staff), `RequireAdmin` (staff).

### Conventions

**Backend**

- Новые сущности — в `core/models/`, затем serializer + ViewSet, регистрация в `core/urls.py`
- Права по умолчанию — через `RolePermission`; admin-only — `IsAdminUser`
- Не класть бизнес-логику в `admin.py`; сложные действия — во views/services рядом с доменом
- Миграции создавать через `makemigrations`, не править применённые руками без необходимости

**Frontend**

- Вызовы API только через `frontend/src/api/` (`http` + модули), не через сырой `fetch` в страницах
- Типы домена — в `frontend/src/types/`; держать согласованными с serializers
- Страницы — в `pages/<domain>/`; guard'ы маршрутов — в `auth/`
- Стили — CSS рядом с компонентом/страницей (как сейчас), без нового UI-фреймворка без явного запроса

## Boundaries

**Запрещено (даже «для проверки» / «временно»)**

- Удалять, сбрасывать или чистить БД и её данные
- Команды и флаги вроде: `docker compose down -v`, `dropdb`, `DROP DATABASE`, `TRUNCATE`, `DELETE FROM` без фильтра задачи, `flush`, `reset_db`, пересоздание volume `postgres_data`
- Запускать destructive migrate (`migrate zero` и аналоги) без явной просьбы пользователя
- Предлагать «чистый старт с пустой БД» как решение проблемы

Если для отладки кажется нужен сброс БД — **остановитьcя и спросить**. Исключение только при прямой команде пользователя сделать это.

**Не трогать без явной просьбы**

- `.env`, секреты, credentials
- `frontend/dist/`, `backend/staticfiles/`, `node_modules/`, `.venv/`
- Production-секреты Amvera / CI

**Спросить перед изменением**

- Схема БД / миграции с потерей данных
- Модель ролей и `RolePermission`
- Dockerfile / `entrypoint.sh` / Amvera-конфиг, если задача не про деплой

**Можно менять свободно**

- `backend/core/` (models, views, serializers, tests) в рамках задачи
- `frontend/src/` в рамках задачи
- README при изменении команд запуска или портов

## Данные игроков (NTRP, очки, город)

Источник — Google Sheets лиги, 4 таблицы: М/Ж × одиночный/парный. Выжимка лежит в
`backend/core/data/ntrp_players.json`: 203 человека, у каждого очки и NTRP **отдельно**
для одиночного и парного разряда, город, год рождения и логин.

- Схема: `Player.city`, `birth_year`, `ntrp_singles`, `ntrp_doubles`,
  `points_singles`, `points_doubles` (миграция `0010_player_ntrp_city_points`).
- Сид: `python manage.py seed_players [--dry-run] [--password ...]`. Идемпотентен:
  ищет `Player` по email `{login}@tennis.local`, повторный запуск обновляет записи.
- Аккаунты: роль `player`, пароль по умолчанию `Tennis2026!`, логин — транслит
  `фамилия_имя` (`lashkov_vladislav`, `khrulev_anton`).
- `Player.rating` заполняется очками одиночного разряда (у парников — парного):
  именно на нём работают сортировка списка игроков и лимиты `min_rating`/`max_rating`.
- Коды регионов из исходника: ВОЛ→Вологда, ЧРП→Череповец, ВЛГ→Вологодская область,
  АРХ→Архангельск, РЫБ→Рыбинск, СПБ→Санкт-Петербург, САР→Саратов, СМР→Самара.
  САР/СМР/ВЛГ — предположение, расшифровки в таблице нет.
- Пагинация: `core.pagination.StandardPagination` — поддерживает `?page_size=`
  (максимум 500). Без него рейтинг обрезался на 50 записях, т.к. `PageNumberPagination`
  игнорирует `page_size` по умолчанию.
- Фронт: на «Рейтинге» и в топ-10 на главной есть переключатель разряда
  (одиночный/парный); в рейтинг попадают только те, у кого есть очки в этом разряде.

## Заявки и пары (2026-11-03)

- `TournamentRegistration.invited_by` — кто пригласил игрока в пару.
- `POST /api/registrations/` принимает `partner` (только парный турнир): создаются
  две заявки с общим `pair_id` (следующий свободный номер). Актор-игрок → обе
  `pending`, у партнёрской заполнен `invited_by`; staff/organizer → обе сразу `approved`.
- `POST /api/registrations/{id}/approve/` — для парного турнира подтверждает всю пару.
- `POST /api/registrations/{id}/confirm/` — партнёр подтверждает приглашение, пара
  становится `approved`. Разрешено самому игроку (и админу/организатору).
- `DELETE /api/registrations/{id}/` — удаляет заявку; если у неё есть `pair_id`,
  удаляется вся пара. Доступно organizer и staff (обычный игрок — нет).
- `frontend/src/components/PlayerPicker.tsx` — селект с поиском (фамилия/имя/город) и
  инлайн-созданием игрока (`allowCreate`). Используется в блоке «Заявить участников»
  и в выборе партнёра. Новый игрок создаётся через `POST /api/players/`, email
  генерируется как `player_<timestamp>@tennis.local`, если поле пустое.
- Посев: `recalculate_seeds()` ставит `seed` 1–4 первым четырём участникам по
  рейтингу (пересчитывается при создании/подтверждении/удалении заявки и при
  генерации сетки, но **не** на GET-списке — иначе ручной посев не сохранить),
  остальным — `null`.
  **Рейтинг зависит от разряда:** одиночный турнир — `Player.points_singles`,
  парный — сумма `Player.points_doubles` обоих партнёров. Обе записи пары получают
  один номер посева. Список заявок: парный турнир — по `pair_rating` (Subquery по
  `pair_id` и `points_doubles`), одиночный — по `-player__points_singles`.
  Лимиты `min_rating`/`max_rating` тоже сравниваются с очками нужного разряда.
- `Player.rating` — устаревшее поле: сидер пишет туда `points_singles`, в расчётах
  посева и лимитов оно больше не участвует.
- Статусы турнира: `draft` Черновик → `registration` Регистрация открыта →
  `registration_closed` Регистрация закрыта → `in_progress` Турнир начался →
  `summing_up` Подводим итоги → `finished` Завершён (миграция `0012_tournament_statuses`).
  Заявки игроков принимаются только при статусе `registration`.
- Таблица участников на странице турнира: одна строка = один игрок. Колонки: Посев,  Игрок, Город, Год рождения, Пол, Очки, Очки пары, NTRP. В «Посеве» — порядковый
  номер по рейтингу (у пары одинаковый для обоих), первые 4 выделены ★ и акцентным
  фоном, остальные — обычным серым номером. Очки/NTRP — по разряду турнира;
  «Очки пары» — сумма парных очков пары (в одиночном — «—»). Партнёры идут
  отдельными строками, каждая пара — отдельный `<tbody>`, пары выделены
  чередующимся фоном, жирной линией сверху и пунктиром между партнёрами.
- `Player.is_ftvo` (boolean, миграция `0013_player_is_ftvo`) — отдельный критерий
  игрока, отдаётся в API (`/api/players/`), в таблицу турнира не выводится.
- Игрок обязан указать партнёра в парном турнире (иначе 400). Админ может заявить
  одиночную заявку без пары — на этом построено старое добавление из формы турнира.
- Проверка `tournament.status == registration` действует только для заявок игроков:
  staff/organizer может заявлять игроков в турнир любого статуса.
- `Tournament.players` — `through_fields=("tournament", "player")`, иначе Django
  падает с fields.E335: у `TournamentRegistration` два FK на `Player`.

## Двойное выбывание / сетка с подвалом (`double_elim`)

Схема как в Excel «сетка 16 (с подвалом)» — **28 матчей** на 16 участников:

| Блок | Матчей | Что это |
|---|---|---|
| Основная 1/8 | 8 | первые пары |
| Основная 1/4 | 4 | победители 1/8 |
| Подвал 1/4 (9–16) | 4 | проигравшие 1/8 |
| Подвал 1/4 (5–8) | 4 | победители подвала + проигравшие 1/4 основной |
| Основная 1/4-2 | 4 | победители 1/4 основной + победители подвала 5–8 |
| 1/2 | 2 | |
| Финал + 3-е место | 2 | проигравшие 1/2 играют за 3-е место |

- Поля `Match`: `bracket` (`winners`/`consolation`/`third_place`), `group` (`5-8`, `9-16`),
  `next_match` + `next_slot`, `loser_next_match` + `loser_next_slot`
  (миграции `0014_match_bracket_links`, `0015_match_group`).
- Посев: 1 — верхний слот, 2 — нижний, 3 — низ первой половины, 4 — верх второй
  половины (`_seed_slots`); остальные участники распределяются по свободным слотам
  случайно.
- Генерация «только сеяные»: `POST /api/tournaments/{id}/generate_bracket/` с телом
  `{"only_seeded": true}` ставит в сетку только 4 сеяных, остальные слоты остаются
  пустыми — админ заполняет вручную через редактирование матчей. На странице сетки
  для этого есть галочка «Только сеяные». Для форматов, отличных от 28-матчевой
  сетки, работает `_generate_main_with_third` (олимпийка + 3-е место).
- `MatchViewSet._advance`: победитель идёт в `next_match`, проигравший — в
  `loser_next_match`. Цепочки проверены: 1/8 → 1/4 основной и подвал;
  1/4 основной → 1/4-2 основной (слот 1) и подвал 5–8 (слот 2); подвал 9–16 →
  подвал 5–8 (слот 1); подвал 5–8 → 1/4-2 основной (слот 2); 1/2 → финал и 3-е место.
- Форма матча (`MatchFormPage`): «Победитель/Победившая пара» видны всегда,
  независимо от статуса; при выборе победителя бэкенд сам двигает игроков по сетке.
  Счёт вводится **таблицей по сетам** (`set1_home/away` … `set3_home/away`),
  отдельного текстового поля «Счёт» больше нет. `MatchSerializer.validate` собирает
  строку `score` из заполненных сетов — и перезаписывает её пустой, если все сеты
  очистили (раньше при очистке оставался старый текст).
- Для числа участников, отличного от 16, работает запасная схема
  `_generate_main_with_third`: олимпийка + матч за 3-е место.
- UI: `DoubleElimBracket.tsx` — одна горизонтальная «доска»: слева подвал
  (1/4 5–8, затем 1/4 9–16), справа основная сетка (1/8, 1/4, 1/4, 1/2, финал),
  матч за 3-е место — под финалом. Нумерация как в Excel-образце: в подвале 5–8
  у второго игрока номера 1–4, под блоками — «Победитель на 8/7/6/5» (синим); во
  втором круге основной сетки под блоками — «Проигравший на 2/1/4/3» (красным);
  в третьем круге (1/4-2) у второго игрока номера 5–8. Больше нигде номеров нет.
  У сеяных — бейдж «№1–4». Счёт по сетам выводится **справа от имени** в каждой
  строке пары (`6 6` / `3 2`), а не отдельной строкой под игроками; если сетов нет,
  строка `score` парсится в те же числа. Статус матча не выводится.
- Расписание: `Tournament.courts` (по умолчанию 4), `match_duration_minutes` (60),
  `saturday_start_time` и `sunday_start_time` (09:00). `Match.court`.
  `POST /api/tournaments/{id}/generate_schedule/` раскладывает **только текущий
  игровой день** (первый день с незавершёнными матчами; если все завершены —
  следующий после последнего). Готовыми считаются матчи, где известны обе стороны;
  заполняются свободные слоты дня, прошедшие слоты сегодняшнего дня не используются.
  Дни **после** текущего очищаются (`cleared` в ответе) — их нельзя планировать,
  пока не доигран текущий. `?reset=true` в теле — очистить и пересобрать незавершённые
  матчи текущего дня (сыгранные не трогаются). `SCHEDULE_ORDER` — порядок 1/8 → подвал 9–16 → 1/4 →
  подвал 5–8 → 1/4-2 → 1/2 → финал → 3-е место. Каждый день стартует от своего
  времени (суббота/воскресенье), окно до 21:00, слоты по `match_duration_minutes`.
  Время хранится в `TIME_ZONE = "Europe/Moscow"`. Дату/время и корт можно править
  вручную в форме матча. Если целевой день оказался в прошлом, планирование
  переносится на сегодня. `_occupied_slots` игнорирует матчи без корта и временем
  до старта дня.
- `GET /api/tournaments/{id}/schedule_template/?days=3` — **предпросмотр** плана
  на ближайшие дни: берёт все незавершённые матчи, включая ещё не известных
  участников (TBD), и раскладывает по дням, ничего не сохраняя. Только staff/organizer.
  Номер дня считается от `tournament.start_date`, а не от начала шаблона.
- На странице турнира у расписания: кнопки «Составить расписание» (текущий день;
  при наличии будущих дней спрашивает подтверждение, т.к. они будут очищены),
  «Пересобрать день» (с подтверждением; чистит несыгранные матчи дня и раскладывает
  заново) и «Шаблон следующих дней» (предпросмотр, пунктирная рамка, «не сохраняется»),
  строка статуса «Текущий день — …: сыграно X из Y. Следующий день откроется,
  когда завершатся матчи этого дня», а также количество несыгранных матчей.
  Матчи без времени показываются блоком «Ещё не в расписании».
  Сообщение после генерации пишет, сколько матчей будущих дней очищено.
- ⚠️ Обычным пользователям (не staff/organizer) показывается только **готовое**
  расписание: матчи с назначенным временем и известными обеими сторонами. Матчи
  с `TBD` и блок «Ещё не в расписании» скрыты; если показывать нечего — «Расписание
  пока не опубликовано…». Счётчик в заголовке у гостя тоже считает только готовые.
- Страница турнира показывает не общий список матчей, а **расписание по дням**:
  матчи группируются по дате `scheduled_at` (локальная). Внутри дня — сетка
  «время × корт»: строка = время, колонка = корт, в ячейке матчи (пара/игроки,
  раунд и счёт). Матчи без времени — блок «Ещё не в расписании». Статус матча в
  расписании не выводится.

## Формат сетов, фото, регламент, итоги (2026-11-04)

- `Tournament.set_games` — `4` или `6` («сет до»); `third_set_super_tiebreak` —
  ровно `True` = 3-й сет тай-брейк до 10, `False` = полный сет. Задаётся в форме
  турнира, показывается в карточке турнира и подсказкой под таблицей сетов в матче.
  Серверной валидации счёта под формат **нет** — только подсказка в UI.
- `Match.set1_home/away`, `set2_*`, `set3_*` — `PositiveSmallIntegerField null`.
  Домашняя сторона = `player1` / `pair1_player2`, гостевая = `player2` / `pair2_player2`.
- `Tournament.regulation` — `FileField(upload_to="regulations/")`;
  `summary_text` — текст итогов; `TournamentPhoto` — фото (`tournaments/photos/`,
  `caption`, `order`). Миграция `0019_match_sets_photos`.
- Загрузка: `POST /api/tournaments/{id}/photos/` (multipart, поле `image`),
  `DELETE /api/tournaments/{id}/photos/{photo_id}/`,
  `POST /api/tournaments/{id}/regulation/` (поле `file`). Права — staff/organizer.
- **`pillow` обязателен** в `backend/requirements.txt`: без него Django падает на
  `ImageField` с `fields.E210` ещё до старта (было поймано при первом запуске).
- `MEDIA_URL = "/media/"`, `MEDIA_ROOT = backend/media`. Раздача — через

## Очки за турнир (2026-11-04)

Правила — с последнего листа таблицы игроков (`gid=1971746850`), скопированы
в `backend/core/services/points.py` (словари `OLYMPIC`, `DOUBLE_ELIM`, `GROUP`).

- `Tournament.points_category`: `""` (не начислять), `two_day`, `one_day`,
  `veterans`, `region`. Выбирается в форме турнира.
- Схема определяется **по фактической сетке**, а не только по `format`:
  есть матчи `consolation` → двойное выбывание (места 1, 2, 3, 4, 5-8, 9-12, 13-16),
  `round_robin` → групповой (места по числу побед и разнице сетов),
  иначе олимпийка (1, 2, 3, 4, 1/4, 1/8, 1/16…).
- Число участников: парный турнир — число пар (`pair_id`), одиночный — число
  заявок `approved`. Бакеты: `8≤`, `9-12`, `13-16`, `17-24`, `25-32`, `33-48`, `49-64`;
  для групповой таблицы сетка другая — `5`, `6`, `8`, `9-10`, `12`, и очки есть
  только за первые места из списка.
- `POST /api/tournaments/{id}/award_points/` — считает и начисляет. Идемпотентно:
  прежние начисления снимаются, затем начисляются заново (проверено: повторный
  вызов даёт дельту 0). Очки пишутся в `Player.points_singles` (одиночный) или
  `points_doubles` (парный), история — `TournamentPointsAward`
  (турнир, игрок, место, очки). Удаление турнира снимает начисленные очки
  (`TournamentViewSet.perform_destroy` → `revert_awards`).
- При переводе турнира в статус «Завершён» очки начисляются автоматически, только
  если **все непустые матчи завершены** (`TournamentViewSet.perform_update`).
  Правка любого матча завершённого турнира пересчитывает начисления
  (`MatchViewSet.perform_update`), поэтому исправленный счёт не оставляет старые очки.
  Ручная кнопка на странице итогов остаётся для пересчёта.
- `apply_awards`/`revert_awards` берут `select_for_update` на турнир, плюс
  `UniqueConstraint(tournament, player)` (миграция `0023_unique_points_award`) —
  параллельные нажатия не задвоят очки.
- В UI: блок «Кому сколько очков начислено» — **в самом низу** страницы итогов
  (после результатов матчей), таблица доступна всем, кнопка пересчёта — только
  staff/organizer. Для парного разряда — пояснение, что очки получает каждый игрок.
- `TournamentPointsAwardSerializer` отдаёт `PlayerBriefSerializer` (без email/phone),
  а не полный профиль.
- ⚠️ Проверенные суммы: олимпийка 16 участников / `two_day` = 175
  (40+30+22+15+9×4+4×8); олимпийка 32 / `region` = 595; двойное выбывание 16 /
  `two_day` = 167 (40+30+22+15+9×4+4×4+2×4); круговой 8 / `one_day` = 14
  (очки только за 1–4 места).

## Возрастной ценз, WC и статусы (2026-11-04)

- `Tournament.age_min` — минимальный возраст **каждого** игрока;
  `Tournament.pair_age_sum_min` — минимальная **сумма возрастов пары**.
  Проверка в `core/services/age.py` (`player_age`, `age_check`) на дату
  `tournament.start_date`. Возраст берётся из `Player.birth_date`, иначе
  из `birth_year`; неизвестный возраст заявку **не блокирует**.
- `TournamentRegistration.wildcard` (WC). Сценарии:
  - игрок подаёт заявку → статус `pending` независимо от возраста,
    в API у заявки есть `age_ok`;
  - админ добавляет участника сам (`POST /registrations/`) → сразу `approved`,
    а если возраст не проходит — `wildcard=True`;
  - `POST /registrations/{id}/approve/` с телом `{"wildcard": true}` допускает
    «непроходящего»; без флага вернёт **400** с текстом причины и подсказкой
    «Подтвердите заявку с WC»;
  - игрок подтверждает приглашение в пару (`confirm`) → при провале по возрасту
    получает 400 «Организатор может допустить вас с WC», пара остаётся `pending`.
- UI: в форме турнира — «Возраст от»; «Сумма возрастов пары от» показывается
  только для парного турнира. На странице турнира у pending-заявок бейдж
  «не проходит по возрасту» и кнопка «Допустить с WC», у допущенных — бейдж «WC»,
  игроку показывается предупреждение ещё до подачи.

### Статус матча больше не выбирается вручную

- Из формы матча убраны «Категория» и «Статус». Категория (`gender_type`)
  принудительно берётся из турнира в `MatchSerializer.validate`, клиент её
  не меняет.
- Статус вычисляется в `MatchSerializer.validate`: при сохранении сетов или
  победителя → `finished`, при очистке → `scheduled`. Статус `walkover`
  сохраняется, пока не введён реальный счёт.
- ⚠️ На фронте статус матча **не выводится нигде**: убран из страницы матча,
  списка матчей (колонка и фильтр) и карточки сетки. Остался только в API/фильтрах.
- «Идёт» — не хранится: в API фильтр `?status=in_progress` отдаёт матчи, где время
  уже наступило, а результата нет; `?status=scheduled` — только ещё не начавшиеся.
  На клиенте этот расчёт больше не используется.
- Миграция `0022_match_status_from_result` проставила `finished` всем матчам
  с победителем или счётом (кроме `walkover`). Страница матча показывает «Счёт»
  всегда: строку из `score`, а если её нет — собранную из сетов; пусто → «—».

## ⚠️ Олимпийская сетка была заглушкой

До 2026-11-04 `_gen_single_elim` и `_gen_single_elim_doubles` создавали **только
первый круг** — турнир `single_elim` дальше не игрался. Теперь и одиночная, и
парная олимпийка идут через `_generate_main_with_third` (полные круги, связи
`next_match`, матч за 3-е место). `_gen_single_elim` удалён,
`_gen_single_elim_doubles` остался без вызовов.

- `_seed_slots`: при недоборе участников пустые слоты (bye) отдаются сеяным —
  партнёрский слот сеяного (`index ^ 1`) не заполняется. Раньше bye-ы падали
  случайно и могли оставить целую четверть без игроков.
- `_pass_byes` (в `_generate_main_with_third`): если в матче заполнена только одна
  сторона, она автоматически проходит дальше (`winner`, статус `walkover`),
  каскадом по кругам. При `only_seeded` bye-ы **не** применяются.

## Локальный запуск на Windows (эта машина)
- `\` в PowerShell не является переносом строки — использовать обратный апостроф.
- `backend/entrypoint.sh` в Windows-чекауте получает CRLF, из-за чего контейнер падает
  с `exec ./entrypoint.sh: no such file or directory`. Обход:
  `--entrypoint sh ... -c "python manage.py migrate --noinput && exec gunicorn config.wsgi:application ..."`.
  Нормальное лечение — `.gitattributes` с `*.sh text eol=lf` и пересборка образа.
- Порт 5432 занят другим проектом → в `.env` ставим `POSTGRES_PORT=5433`.
- Изнутри контейнера `POSTGRES_HOST=localhost` не работает, нужен `host.docker.internal`.
